## Bugs in the existing code to fix first

1. Rows do not refresh after an action. `IssueList` accepts `onAfterAction`, but
   `src/widgets/registry.tsx` never passes it and `WidgetContext` offers no refresh to
   pass. The claim in `dashboard-vision.md` that refresh on success is handled by
   `IssueList` is therefore wrong, and should be corrected there with the fix.
2. Pinning or unpinning a repo does not refetch widgets that have cached data.
   `src/components/Dashboard.tsx` auto-fetches only when `data === null`, and the
   cache key does not include the pinned set. The triage queue in #14 would be stale.
3. `createLabel` in `src/api/github.ts` does not check `res.ok`. The label sync in #12
   reuses it and would report failures as "created". `createMilestone` has the same
   flaw.

Later on 2026-11-23 all three were fixed on `feature/phase3-actions` (`6b70c0e` and
`1a0bf5f`), with tests for the widgets, the widget cache and
the API client. The combined tree passes 40 tests, the type check, the build and lint
on the local Node version; the Node 20 that CI uses has not been run. The UI was still
not exercised in a browser. Whether GitHub's search index reflects an action by the
time of the refetch is unverified, so a handled row may reappear briefly.

These were noticed during the fixes and left alone:

- In the Markdown import, a failed `createIssue` is only logged to the console, its
  children are skipped and the Markdown text is cleared, so the user can lose work.
- The widget cache does not record the viewer, so switching GitHub account in the same
  browser can show the previous account's rows.
- A `localStorage` write failure discards a successful widget fetch as an error.
- If the user leaves the dashboard and returns while a row action is still running, the
  new instance is not told when it finishes and the row stays until the next refresh.

## Problems found in the issues

None of these have been edited or commented on GitHub.

- **The issues do not account for the Phase 3 branch.** #13 calls itself the first
  Phase 3 write action, but approve, merge and close are already in `138658b`. For #15,
  `addLabels` exists there; label removal, and closing as "not planned", do not.
- **Two lists of repos.** Triage (#14) is scoped to pinned repos in localStorage, the
  runner (#18) to `nightshift/repos.json`. A promoted issue might never run, and an
  allowlisted repo's proposals might never be seen.
- **`SearchIssue` has no `body` field.** #14 needs it to flag a missing "Verify with".
- **The runner's hard rules rest on its prompt alone.** `master` has no branch
  protection and the repository has no rulesets. The only workflow runs on pushes to
  `master` or manual dispatch, so draft PRs from the runner would get no checks.
- **Issues can change after promotion.** The repository is public and authors can edit
  their own issues, including the "Verify with" command the runner executes. #18
  should pin the promoted body or check that it is unchanged.
- **"Verify with" is inconsistent.** #11 requires the runner to block issues that lack
  it, the steps in #18 do not mention that, and none of the stories contain it. It
  also overlaps with `testCommand` in #10 without a stated precedence.
- **The log location is unclear.** #18 commits run logs to `nightshift/log`; #23 and
  #28 give paths under `nightshift/runs/` without naming a branch.
- **#22 looks too large for A1.** It needs label-event history, comments and PR links,
  which the current search results do not provide.
